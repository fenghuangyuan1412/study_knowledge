## 一句话摘要

UI 自动化的失败大多不是「不会写」，而是「写完之后维护不动」。平台化的目标就是把「脚本维护」变成「数据维护」。实现路径有两条——**关键字驱动**（把操作抽象成词，用例变成词序列）与 **POM**（把页面抽象成对象，用例调页面方法）；两者不是二选一，成熟平台通常是「关键字驱动做编排 + POM 做元素管理」。

## 核心内容

1. **为什么脚本会烂掉：三个结构性原因**

   - **元素定位散落**：同一个按钮的定位器在 20 个脚本里各写一遍，页面一改就要改 20 处。
   - **流程与实现耦合**：脚本里混着「业务步骤」和「怎么点」，业务变了要读懂代码才能改。
   - **没有失败证据**：跑失败了只有一个报错，没有截图、没有当时的 DOM，定位全靠复现。

   平台化的本质，就是分别用「元素层」「关键字层」「执行层」把这三点隔离掉。

2. **封装的两个范式**

   | | 关键字驱动（Keyword-Driven） | 页面对象（POM） |
   | --- | --- | --- |
   | 抽象单位 | 一个操作词，如「输入_用户名」「点击_登录」 | 一个页面类，如 `LoginPage` |
   | 用例形态 | 词序列（可存数据库，非代码） | 代码调用页面方法 |
   | 谁维护用例 | 测试人员可在界面上维护 | 通常需要懂代码 |
   | 元素定位放在哪 | 关键字实现内部 | 页面类内部 |
   | 优势 | 业务人员可参与、平台化天然友好 | 结构清晰、贴合面向对象 |
   | 劣势 | 关键字粒度设计难，容易退化成「脚本换皮」 | 页面多了类会爆炸，用例仍是代码 |

   **实践建议**：不要一上来就追求「全关键字、零代码」。更稳的组合是——**元素定位用 Page/Element 表统一管理（POM 的思想），操作步骤用关键字表编排（关键字驱动的思想），底层执行交给统一驱动（如自研 `apprun` 之类的封装工具）**。

3. **平台的四层结构**

   - **元素层**：页面/控件及其定位方式（id / xpath / css / accessibility id）统一存库，支持一个元素多套定位（主备切换）。
   - **关键字层**：把常用操作封装成可配置的词（点击、输入、等待、滑动、断言、截图），支持参数化。
   - **用例层**：由关键字/步骤组成，可参数化、可嵌套调用。
   - **执行层**：套件与计划调度、并发与设备分配、失败重试与截图、报告生成。

4. **WEB 与 APP 的差异（不能直接套用）**

   | 维度 | WEB（Selenium） | APP（Appium） |
   | --- | --- | --- |
   | 定位手段 | id / css / xpath / 文本 | accessibility id / xpath / 控件层级 |
   | 环境 | 浏览器 + driver 版本匹配 | 真机/模拟器 + 系统版本 + 设备集群 |
   | 稳定性 | 隐性等待、动态渲染、iframe | 弹窗、权限、弱网、系统手势干扰 |
   | 规模化难点 | 多浏览器兼容矩阵 | **多设备并行**与设备资源调度 |

   APP 平台比 WEB 平台多出的核心问题就是**设备维度**：如何登记设备、分配设备、并行跑、回收设备，以及不同系统版本下的控件差异。

5. **让 UI 自动化「不那么脆」的工程手段**

   - **显式等待替代 sleep**：按条件等待（元素可见/可点击）而不是拍脑袋等几秒。
   - **失败自动截图 + 保留页面源码**：报告里直接能看到现场，这是平台相对脚本的最大价值之一。
   - **稳定的定位策略优先级**：唯一的业务属性 > id > 文本 > 层级 xpath；能加测试专用属性就让开发加。
   - **用例幂等**：用例自身准备数据、清理数据，不依赖上一条用例的执行结果（需要链路时用流程编排显式表达）。
   - **失败重试要谨慎**：重试能掩盖真实的不稳定；只在明确是环境抖动时启用，并在报告中标注「重试后通过」。

## 关键概念与提法

- **关键字驱动**：用「操作词」描述用例，把实现细节下沉到关键字实现里。
- **POM（Page Object Model）**：以页面为单位封装元素定位与页面操作，用例只调页面方法。
- **元素定位优先级**：选择定位方式时按稳定性排序，优先业务属性和唯一 id。
- **显式等待**：等待某个条件成立再继续，而不是固定休眠。
- **设备集群 / 多设备并行**：APP 自动化规模化的关键，涉及设备注册、分配与回收。
- **失败证据链**：截图 + 日志 + 页面源码 + 请求响应，是平台化报告区别于脚本输出的核心。

## 结论与影响

- UI 自动化的评价标准不是「能跑通」，而是**页面改版后修复成本有多低**——这正是封装要解决的问题。
- 关键字驱动与 POM 各有所长，成熟方案是「元素层用 POM 思想、用例层用关键字编排」。
- WEB 与 APP 平台的骨架同构、细节差异大，APP 的额外复杂度几乎全在**设备维度**。
- 失败证据链（截图/源码/日志）是平台相对裸脚本最实在的增值点，值得优先做。
