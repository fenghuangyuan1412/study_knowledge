## 一句话摘要

大纲新增的这条线回答一个具体问题：**如何让大模型真正「动手」做测试**，而不只是「聊测试」。答案分三层——用 MCP 协议把测试能力标准化地暴露给模型，用 Skill 封装把一类能力打包成可加载单元，用 Agent 架构把「模型 + 工具 + 记忆」编排成能自主完成任务的执行体。

## 核心内容

1. **为什么需要 MCP：模型与工具之间的「插座标准」**

   大模型本身只能生成文本，要让它操作外部世界（读文件、调接口、跑用例、查数据库），必须有人把「可调用的能力」按某种约定暴露出来。MCP（Model Context Protocol）就是这套约定。它把系统拆成两个角色：

   - **MCP 服务端（Server）**：能力的提供方。它对外声明「我有哪些工具（tools）、哪些资源（resources）、哪些提示模板（prompts）」，并负责实际执行。
   - **MCP 客户端（Client）**：能力的消费方，通常内嵌在 Agent 宿主里。它负责连接服务端、把服务端声明的能力转成模型能理解的函数描述、在模型决定调用时发起真实调用并把结果回填给模型。

   价值在于**解耦**：测试能力实现一次（服务端），任何支持 MCP 的客户端都能复用；换模型、换宿主不用改测试代码。

2. **Skill 封装：把「一类能力」打包成可加载单元**

   MCP 解决的是「运行时怎么调」，Skill 解决的是「怎么把能力成套交付」。一个 Skill 通常是一个目录，含：

   - **说明文件**（技能名、适用场景、何时触发、有哪些子能力）——这是给模型看的「说明书」，决定模型能否在正确时机想起它；
   - **脚本/代码**：真正干活的实现；
   - **资源与模板**：语料、配置、提示词模板等；
   - **元数据**：版本、依赖、权限范围。

   关键认知：**Skill 的质量上限由「说明文件」决定，而不是由代码决定**。模型是依据描述来选择技能的——描述写得含糊，再强的实现也不会被调用。这与传统「写好 API 文档」的直觉一致，但要求更高：描述是写给概率模型读的。

3. **Agent 架构：把模型、工具、记忆编排成执行体**

   Agent 的核心不是「更聪明的模型」，而是一个循环：**观察 → 思考（选工具）→ 行动（调工具）→ 观察结果 → 再思考**，直到任务完成或触发终止条件。从 0 实现一个 Agent 需要解决四件事：

   | 组成 | 要解决的问题 | 典型做法 |
   | --- | --- | --- |
   | 规划 | 任务怎么拆成多步 | 让模型输出步骤，或预定义工作流 |
   | 工具调用 | 模型怎么表达「我要调哪个工具、传什么参」 | 结构化输出（函数调用 / JSON） |
   | 记忆 | 上下文太长怎么办、跨会话怎么记住 | 短期上下文窗口 + 长期向量库检索 |
   | 终止与纠错 | 什么时候停、调用失败怎么回退 | 最大轮次、错误回填让模型重试、人工确认点 |

4. **对测试工作的直接落点**

   - **把测试能力 MCP 化**：把「跑一批接口用例」「查某个环境的服务状态」「生成测试报告」包装成 MCP 工具，模型就能被要求「先查环境、再跑回归、失败则附上日志」。
   - **把测试知识 Skill 化**：把「本项目的用例设计规范」「接口约定」「常见缺陷模式」做成 Skill，让智能体在写用例时自动遵循团队规范。
   - **边界要清楚**：智能体适合做「探索、生成、编排、归因」；对「是否放行上线」这类判断，仍应保留人工确认点。

## 关键概念与提法

- **MCP（Model Context Protocol）**：模型与外部工具/数据源之间的标准调用协议，分服务端（提供能力）与客户端（消费能力）两侧。
- **工具（tool）声明**：服务端向模型暴露的可调用能力描述，包含名称、用途、参数结构；描述质量直接决定模型是否会正确使用。
- **Skill**：把一类能力及其说明、脚本、资源打包成的可加载单元；区别于单次提示词，它是可复用、可版本化的交付物。
- **Agent**：以「规划—工具调用—记忆—终止」为骨架的自主执行体，本质是一个受控的循环，而不是单一模型调用。
- **上下文工程**：为模型挑选、压缩、组织输入的过程；在测试场景中表现为「把哪些用例、日志、规范放进提示词」。
- **人在回路（human-in-the-loop）**：在关键节点要求人工确认，防止智能体自主执行高风险操作。

## 结论与影响

- 智能体测试开发的门槛**不在模型，而在「可被调用的测试能力」**：没有稳定、可编程的自动化资产，智能体无从发力——这与第 01 条「先有自动化，再谈平台化」是同一逻辑的延伸。
- Skill/MCP 的说明文件是新的「接口文档」，**面向模型编写**，需要把「何时用、怎么用、边界在哪」写清楚。
- 落地时应从低风险、高频、结果可验证的任务切入（如用例草稿生成、失败日志归因），把「是否放行」留给人工。
