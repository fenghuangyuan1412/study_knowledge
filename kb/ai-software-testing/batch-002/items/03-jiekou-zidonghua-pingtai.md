## 一句话摘要

接口自动化平台是把「写脚本跑接口」升级为「配数据管用例、点按钮跑执行、看报告定位问题」的系统。它的技术栈（Vue + Flask + MySQL）只是外壳，真正的设计难点是**三张关系**：用例与流程的关系、数据与执行的关系、执行与报告的关系。把这三张关系理清，平台就成立了。

## 核心内容

1. **推荐的入手顺序：接口平台 → WEB 平台 → APP 平台**

   接口平台是最适合做「第一个平台」的：它不依赖浏览器和真机环境、执行速度快、失败原因清晰（状态码 + 响应体）、调试成本低。WEB/APP 平台在架构上与它高度同构，只是把底层执行器从 `requests` 换成 `selenium` / `appium`。**先做接口平台，再复制范式**，是效率最高的路径。

2. **数据模型：先想清楚「谁和谁是一对多」**

   | 实体 | 说明 | 关键关系 |
   | --- | --- | --- |
   | 项目 | 一个被测系统的边界 | 项目 1—N 模块、环境、用例 |
   | 接口 | 一条 API 的定义（路径、方法、请求头/体结构） | 接口 1—N 用例 |
   | 用例 | 一次具体调用（入参、断言、前置/后置） | 用例 N—N 流程 |
   | 流程（场景） | 多个用例按顺序串联，共享上下文 | 流程 1—N 用例（有序） |
   | 套件 | 一批用例/流程的集合，执行的最小调度单位 | 套件 N—N 用例/流程 |
   | 执行记录 / 报告 | 每次执行的快照与结果明细 | 执行 1—N 用例结果 |

   两个最容易踩的坑：
   - **用例与流程的关联用「有序多对多」**，不能只用外键——顺序本身就是信息，必须显式存 `step_order`。
   - **参数传递要可追溯**：后一步用前一步的返回值（如 token、订单号），必须能看出「这个变量是从哪一步的哪个字段提取出来的」，否则失败时无法定位。

3. **执行器：平台的心脏**

   执行器要解决四件事，缺一个平台就不实用：

   - **数据驱动**：一份用例模板 × 多组数据 = 多条执行。数据源可以是平台内的表格，也可以是上传的 CSV/Excel。
   - **变量与上下文**：支持环境变量（域名、账号）、提取变量（从响应提取）、引用变量（在后续请求中使用）。`context` 文件式的做法便于跨步骤传递。
   - **断言与校验**：状态码、响应字段、响应时间、JSON Schema、数据库比对。断言要能配置「软断言」（失败继续跑）与「硬断言」（失败即中止）。
   - **并发与超时**：批量执行要控制并发数与单次超时，避免把被测环境打挂。

4. **前端：不要为了「像 Postman」而复杂化**

   平台的界面目标不是复刻 Postman，而是**让不写代码的同事也能维护用例**。因此优先做的是：

   - 侧边菜单 + 动态路由（按项目/模块组织）；
   - 用例编辑页：请求方法切换时，请求体编辑区随之切换（form / json / raw）；
   - 表格 + 分页 + 批量删除 + 查询条件的联动（这是使用频率最高的交互，值得打磨）；
   - 执行结果页：通过/失败/跳过计数、每条用例的耗时与失败原因、可下钻到请求与响应原文；
   - 登录态与权限：Axios 请求拦截器统一注入 token，响应拦截器统一处理 401/403；前端路由守卫 + 后端菜单接口配合实现动态路由；`keep-alive` 缓存列表页避免反复加载。

5. **平台联调阶段最容易暴露的问题**

   - **跨域**：前后端分离时浏览器的同源策略会拦截请求，需要后端配置 CORS 或在开发环境用代理转发。
   - **环境切换**：至少要区分「测试/预发」两套环境变量，且切换要作用到整个套件的执行上下文，而不是单条用例。
   - **报告可读性**：只有「失败 N 条」的报告没人看；必须能一眼看到「哪条、为什么、请求发了什么、期望什么、实际什么」。

## 关键概念与提法

- **用例（case）**：一次独立可执行的请求 + 断言组合。
- **流程 / 场景（flow / scene）**：多个用例按序组合，共享上下文，用于验证业务链路。
- **数据驱动**：用外部数据表驱动同一逻辑产生多条执行。
- **上下文（context）**：执行过程中传递变量的容器，实现步骤间的数据引用。
- **执行器（runner）**：真正发请求、跑断言、收集结果的组件，是平台的唯一下沉依赖。
- **断言策略**：软断言（失败继续）与硬断言（失败中止）的取舍。
- **动态路由**：前端根据后端返回的菜单/权限数据动态注册路由。

## 结论与影响

- 平台的复杂度应来自**真实痛点**，而不是架构想象；先把「用例 CRUD + 执行 + 报告」这条主链路跑通，再补环境管理、权限、调度。
- 三张关系（用例↔流程、数据↔执行、执行↔报告）是设计的胜负手，比选 Flask 还是 Django 重要得多。
- 接口平台跑通后，WEB/APP 平台可以复用同一套数据模型与前端骨架，**只替换执行器**。
